大家好，我是溪夜。

AI Coding 降低了开发门槛，很多简单需求只要告诉 Agent，就能得到结果。但当需求变复杂，就容易陷入一轮轮补条件、改方案的返工循环中。即使提前写好设计文档，也不能避免这个问题。

最近几个月，我在多个项目中尝试了 Matt Pocock 的 Skills。它提供了一个反直觉的工作流程，接到需求后会先让 Agent 反向追问用户，把目标、边界先问清楚，才会继续开发。

我的直接感受是，过去很多在开发中才能发现的问题，现在在追问阶段就能被发现并做出决策，AI 的产出质量得到大幅提升。

这套 Skills 原本为软件开发设计，但它在游戏音频的技术选型、产品设计与开发中也很有效。本文会结合一些实例，分享这套工作流的效果。

## 为什么要把需求说清楚
### AI 为什么会做错
常见的 AI 使用方式是：写几句需求，让 AI 直接给方案；若结果不符预期，就给出意见让 AI 返工。简单问题通常调整几次就可以，复杂需求可能要调整很多轮。

产生这个问题的原因是，影响方案的背景、限制和判断标准没有说清楚，这些信息就是本文所说的“上下文”。信息不足时，AI 会自行补全假设，给出一条看似合理的路线。后续设计如果都建立在错误的假设上，就可能产生连锁反应，越做越偏。

不断修正需求，很像边施工边改图纸，对话越来越长，新旧方案和限制条件混在一起，这又会增加两类问题：
- 长上下文中的信息不一定都能被模型有效利用，早期约束可能被忽略
- 上下文压缩会把历史对话整理成摘要，以减少对话上下文窗口占用；如果摘要遗漏了关键条件，后续方案也可能偏离要求

### 模糊的需求
“给我一个五彩斑斓的黑”常被用来调侃模糊的需求，音频工作中也有类似的情况：
- 声音要更大声，但混音中已经没有多少余量
- 音乐主题要更有存在感，但不能让玩家注意到它
- 城市要听起来很热闹，但同时播放的声音不能太多

这些要求只表达了感受，难以转换为具体的修改意见。以“更有力量”为例，它可能指低频更多、起音（Attack）更快，或动态更大。有时需要调整的甚至是动画的命中反馈，让音画共同形成打击感。如果没有说明具体的判断标准，AI 就只能盲猜这里的“力量”到底指什么。

我在《打造高效游戏音频问答知识库》中曾提及：**越详细的上下文，越能获得精准的回答**。应用到需求设计的场景中，就是要把会影响方案选择的条件告诉 AI。

但难点在于，这些条件很难一次写全。很多时候只有看到反例、开始比较方案，才能想起来这些细节。

### 让 AI 反过来问细节
既然很难一次想全所有细节，为什么不利用模型已有的知识，让 AI 先来提问：真正的目标是什么，哪些条件必须成立，哪些可以让步，怎样才算完成？

Matt Pocock 把这种反向追问称为 **Grilling**。用户给出目标后，Agent 根据目标开展追问，信息足够后才会生成方案。这种交互模式叫做“翻转交互模式”（Flipped Interaction Pattern），即由 AI 主动询问完成任务所需的信息。

若将需求讨论中的信息按知识四象限分类，Grilling 的作用会更容易理解：

| 知识四象限    | 在需求中的表现           | Grilling 能做什么        |
| -------- | ----------------- | -------------------- |
| 知道自己知道   | 已经想清楚，也已经说出来      | 确认它们是否属于硬性条件         |
| 知道自己不知道  | 知道这里需要做决定，但还没有选择  | 提供选项、取舍和判断标准，并给出参考建议 |
| 不知道自己知道  | 心里其实有判断，只是没有主动说出来 | 通过边界情况和反例，把隐性经验问出来   |
| 不知道自己不知道 | 还没有意识到这个问题存在      | 根据已有条件提示潜在问题，帮用户探索未知 |

对需求讨论来说，中间两类尤其有用：一类是已经知道要做决定，但还没有决策；另一类是心里已有判断，却没有主动说出来。Grilling 可以帮助比较前者，并挖掘出后者。

缺少上下文时，模型先要猜用户究竟想做什么；Grilling 把猜测改为追问，这种做法不会提升模型的上限，但可以让模型的能力得到更充分的发挥。

## 反向追问的案例
下面通过声音设计、技术选型和复杂音频系统规划三个案例，对比直接提问与先追问再生成方案的差别。

每个案例保留初始问题、关键追问和结果差异。测试在 Codex 中进行，并关闭记忆功能，以减少历史信息对结果的影响。

这里比较的是两种工作方式：直接提问先得到一版方案，Grilling 则在补充条件后再生成方案，结果主要用于观察追问如何改变设计。

### 案例一：拆解火系魔法的声音设计
火系魔法是一个常见的声音设计需求，适合观察：从一句笼统描述到可以开始制作，中间还缺哪些条件。

这个案例聚焦声音设计讨论，适合使用 `grill-me` Skill。

#### 初始问题
> 在一款写实与奇幻并存的开放世界第三人称游戏中，设计一个玩家可频繁使用的火系魔法技能。请直接给出声音设计方案，包含技能阶段与分层思路、音效库素材类型和检索关键词、录制或合成方向、混音策略、空间与距离表现、变体和验收方法。

#### 直接提问的结果
直接产出了一份完整的声音设计方案，从起手、点火、飞行写到命中与余烬，还给出了素材关键词、录制方法、频段分工、变体数量等。

这份答案看似很全，但其中不少内容来自模型自行补充的假设：飞行时间、掠过事件、材质响应、暴击、蓄力，以及每类素材的变体数量，都没有经过确认。

这些设计未必不合理，只是项目不一定需要。在开始制作前，仍要逐项确认或删改，不能直接据此安排制作。

#### 使用 Grilling 得到的结果
Grilling 先确认技能形态、战斗职责、美术风格、动画时序、实现范围和并发规模，这里保留一些具有代表性的问题：
```
Q1：它是火球投射物、近距喷焰、瞬发爆燃、持续引导，还是允许蓄力的混合技能？
Q2：它是低消耗普攻、高伤害主力、控场工具，还是点燃异常状态的起手技能？
Q3：更偏真实燃烧、元素奇幻、远古秘术、炼金工业，还是危险失控？
Q4：从掌心开始聚火到火球脱手，动画预留多长时间？是几乎零前摇，还是有约 100–200 ms 的可感知聚火？
Q5：暴击、击杀、抵抗和免疫是否要由火球本身表达，还是交给独立战斗反馈系统？
Q6：方案需要只覆盖声音制作，还是同时给出适合 Wwise/FMOD 的事件、随机容器、RTPC、并发和距离衰减建议？
Q7：敌人的每颗火球都带危险提示，还是仅在确实威胁本地玩家时触发？
Q8：大型战斗中预计同屏有多少玩家、友军和敌方火球？
```

我按实际需求逐项回答，确认了技能时序、战斗职责、声音身份、系统边界和并发压力，最终方案也随之变得具体：

| 阶段 | 分轨 | 功能 | 音效关键词 |
| --- | --- | --- | --- |
| 输入响应和准备 | `Local_Input`、`Palm_Fire`、`Palm_Magic` | 立即响应按键，准备火焰 | `tiny gas click`、`torch flare short`、`glass harmonic` |
| 释放 | `Release_Air`、`Release_Flame` | 表现手部推出、空气位移和火焰离手 | `short air push`、`tight whoosh`、`flame burst short` |
| 飞行 | `Flight_Fire`、`Flight_Magic` | 火球飞行的过程音效 | `flame whoosh loop`、`fire pass by`、`crystal shimmer subtle` |
| 命中结果 | `Impact_Pressure`、`Impact_Fracture`、`Impact_Magic` | 命中后的受击反馈 | `small air thump`、`dry crack`、`glass ping bright` |
| 状态与失败 | `Burn_Status`、`Blocked`、`Dissipate` | 表现轻灼烧、格挡或免疫、飞行消散 | `ember sizzle`、`shield impact dry`、`flame extinguish` |
| 敌对提示 | `Threat` | 只在敌对火球威胁本地玩家时出现 | `dissonant glass sting`、`projectile close pass` |

声音主体表现燃烧、空气运动和热压，短促的玻璃谐振用来突出魔法感。飞行与命中声从各自的场景位置播放，本地玩家额外获得极短的掌心反馈。

多人战斗中，方案优先削减 NPC 的灼烧和装饰层，再简化远处的飞行声，始终保留玩家输入、基础命中和敌对危险提示。

#### 结果对比
两种方式都能生成完整方案。区别在于，直接提问先给出大量未经确认的设计，需要人再筛选；Grilling 先确认技能职责和制作边界，再据此安排分层、素材和混音。

对这个案例来说，追问最有用的地方，是提前确定哪些声音需要做、承担什么作用，以及并发过高时先舍弃哪些内容。

### 案例二：空间音乐的多点同步
该案例受到《无限暖暖》的 Audiokinetic Blog 技术分享启发：多个木偶怪在关卡中自由移动，每个木偶怪持有一条演唱分轨；在每条分轨空间化的同时，与背景 2D 立体声音乐实现样本级同步。

我想测试的是，不提前告诉 AI 实现方法，它能否通过追问需求，做出同样的 Wwise API 技术选型。

本例使用 GPT-5.5（知识截止日期早于该博客发表日期），并限制测试过程不搜索案例博客。

这个案例聚焦技术选型，同样可以使用 `grill-me` 展开讨论。

#### 初始问题
> 如何用 Wwise 实现游戏里的多轨点声源音乐同步？

#### 直接提问的结果
直接提问得到的方案是：
- 每条音乐分轨（Stem）使用独立的 Music Segment，封装成多个 Event，在不同的 Wwise 游戏对象（Game Object）上同时播放
- 需要隐藏声部时，再按小节（Bar）或网格（Grid）切换到静音 Segment。

回答始终沿着“每条 Stem 都是独立播放对象”的前提继续设计，没有进一步考虑改变素材和播放对象的组织方式。

这个思路与《射雕》在 Audiokinetic Blog 分享的音乐同步方案有相似之处，但 AI 并没有提到这个方案的注意点（要使用相同的流播放、虚拟化、寻址表设置等），并不算一个完整的可执行方案。

#### 使用 Grilling 得到的结果
Grilling 先确认音乐结构、空间表现、同步精度、素材组织方式和引擎接入条件，这里保留一些具有代表性的问题：
```
Q1：这些“轨”是同一首音乐的分轨，比如 drums / bass / melody / ambience，还是场景里多个物体各自有音乐循环，但它们需要共享 BPM、bar、beat？
Q2：演员/怪物的 3D 声音，能不能因为距离太远、转头、遮挡而变得听不清，甚至短暂“脱离音乐编曲”？
Q3：能不能接受“怪物实例”和“音乐声部播放实例”解耦？
Q4：“完全同步”是要求 sample-accurate 级别，还是 musical-tight 级别就可以？
Q5：能不能接受把 3D 演员声部导出成“多通道 carrier”，每个怪物声部占一个 mono channel，而不是在 Wwise 里保持独立 Music Track？
Q6：2D 背景音乐和怪物 carrier 是一个音频文件，还是同一个 Music Segment 里的两个同步音频对象？
Q7：引擎侧能不能接受“四个怪物声部属于同一个 Wwise emitter game object”，而不是四个独立 emitter？
Q8：原型能不能接受少量引擎侧代码，直接调用 Wwise SDK 的 `SetMultiplePositions` / channel emitter 接口？
```

逐项回答后，需求明确了背景音乐保持 2D 播放，四个木偶怪声部（即音乐分轨）跟随木偶怪移动；怪物可以离场被新实例替代，但音乐播放进度不能重置。四个声部与伴奏之间必须采样级同步。

最终结构是：

```text
同一个 Music Segment
├─ 伴奏轨：立体声，保持 2D 播放
└─ 木偶怪声部轨：合并为一个多声道素材
   ├─ 四个声部分别占用独立输入声道
   └─ 通过 AkChannelEmitter 分别指定空间位置
```

四个声部来自同一个播放实例，素材内部保持采样对齐。怪物只提供位置，不再分别启动或停止自己的音乐声部。

更新怪物分轨在空间中的定位时，使用 `AK::SoundEngine::SetMultiplePositions` 的 `AkChannelEmitter` 版重载，在 `AkChannelEmitter` 中指定每个声道的标识掩码和所在的位置，即可让四条音轨的空间位置不断更新。

怪物离场时，对应声道继续播放，只需把位置移到衰减范围外的预设退场点。

#### 结果对比
| 对比项    | 直接提问                                           | Grilling                                           |
| ------ | ---------------------------------------------- | -------------------------------------------------- |
| 同步结构   | 每条 Stem 使用独立 Music Segment，需在同一帧 Post 多个 Event | 同一个 Music Segment 内放置立体声伴奏和木偶怪的多声道素材               |
| 同步精度   | 需要另行确认多个 Game Object 上的播放能否满足逐采样同步要求           | 多个声道来自同一播放实例，素材内部天然样本级对齐                           |
| 运行中显隐  | 所有 Stem 持续播放，再按 Bar 或 Grid 切换静音 Segment        | 音乐实例持续播放，怪物只更新对应声道的位置                              |
| API 判断 | 明确排除 `SetMultiplePositions`                    | 选择 `SetMultiplePositions` 的 `AkChannelEmitter` 重载版 |

直接提问注意到了独立播放对象之间的同步问题，却沿用原来的结构继续设计。

Grilling 则通过追问确认，可以把多个声部合进同一个多声道素材，再分别指定空间位置。它据此找到了 `AkChannelEmitter` 重载及输入声道映射的用法，解决了这个案例最关键的技术选型问题。

### 案例三：开放世界城市人群系统音频
开放世界人群系统是比较复杂的课题，会牵连平台、性能、对白、本地化、世界分区加载等问题。

这类问题更适合 `wayfinder` Skill。它会把复杂需求整理成一张决策地图，记录哪些问题已经有了结论、哪些需要研究或追问，以及它们之间的依赖。每解决一个问题，再继续推进下一步。

每张“决策单”围绕一个待解决的问题展开。有的需要 Grilling，有的需要查资料或制作原型，再根据结果作出决定。

#### 初始问题
> 我要在 UE 和 Wwise 中制作一座开放世界城市，场景里会同时出现大量 NPC。近处希望听到具体人物，远处又要形成自然的群杂和人群规模感，同时不能让 Voice 和 CPU 失控。请制定一套可量产的技术方案。

#### 直接提问的结果
直接提问很快给出了近处个人、中距离人群簇和远处区域环境底声的分层思路，并建议结合距离、优先级（Priority）、播放数量限制（Playback Limit）和虚拟声部（Virtual Voice）控制成本。这可以作为第一版架构草图。

但目标平台、NPC 峰值、必须听清的对白和第三人称监听参考点，都没有经过确认。多语种怎样装包、球场和市场如何响应事件、性能指标怎样验证，也仍需讨论。这份答案提供了技术思路，还不足以让程序、声音设计和本地化团队据此分头制作。

#### 使用 Wayfinder 得到的结果
Wayfinder 先确认平台、人数、体验目标、引擎版本、语言数量和监听方式，研究相关机制后再讨论量产取舍，这里保留一些具有代表性的问题：
```
Q1：目标平台、最低配置，以及典型和极端情况下监听者附近的 NPC 数量是多少？
Q2：哪些内容必须保持清楚？远处人群更偏写实克制，还是明显宏大？
Q3：使用什么 UE/Wwise 版本？是否使用 Mass、StateTree 和 World Partition？是否已有 Voice、CPU、内存和流送预算？
Q4：项目是单机还是多人？需要支持多少种语言？主要听音参考点是相机还是角色？
Q5：近处普通小组对话是否需要动画同步、可中断恢复的有状态会话？
Q6：六种配音语言全部随本体安装，还是作为可选语言包？
Q7：人群使用严格独占预算，还是采用软目标加硬上限，并允许受保护内容随时收回？
```

我根据项目需求逐项回答。Wayfinder 随后建立决策地图，把工作拆成体验与预算、官方机制研究、人群音频细节层级（Crowd Audio LOD）、内容制作流程、Xbox Series S 验证和最终方案六部分。

整套方案可以概括为：**近处听到少量具体人物，中距离用带方向的人群簇表现群杂，远处用区域环境底声维持规模感，任务和战斗内容单独保护。**

| 层级    | 玩家听到什么             | 实现方式                                     |
| ----- | ------------------ | ---------------------------------------- |
| 受保护内容 | 任务、同伴和近身战斗始终清楚     | 独立路径和预留容量，不计入人群上限                        |
| 近身人物  | 能听出谁在说、来自哪个方向      | UE 选出少量 NPC，分配池化的 `AkGameObject`         |
| 普通小组  | 两三个人围绕同一话题短暂交流     | 按角色、轮次、应答关系和冷却时间调度对话                     |
| 中距离人群 | 多个方向上的群杂和局部密度      | 少量聚合发声体，通过 `SetMultiplePositions` 设置代表位置 |
| 远端区域  | 保持城市规模感，听得出不同区域和事件 | 为商务区、市场、球场等地点（POI）配置环境底声和事件层             |

UE 负责筛选和排序 NPC、统计人群、管理可复用的发声体，并通过迟滞避免频繁切换；Wwise 负责素材变化、空间化、混音和最终播放数量限制。

第三人称监听采用相机上的 Listener 和角色上的 Distance Probe，分别提供监听位置与距离衰减参考。NPC 的批量筛选交给 Mass，Wwise 的播放限制、优先级和虚拟声部作为后续保护。

内容制作也有了对应模板：区域配置（`POI Profile`）、小组动态 VO（`Call/Response Scene`）、精选表演（`Featured Performance`）、人群簇群杂（`Cluster Walla`），以及六语种可选语言包。

Xbox Series S 验证计划同时覆盖 Voice 数量、CPU、内存、流送，以及对白能否听清、人群规模感和切换听感。24/32 Voice 等数字是原型阶段的起始预算，仍需实测调整。

#### 结果对比

| 对比项  | 直接提问                        | Wayfinder                                 |
| ---- | --------------------------- | ----------------------------------------- |
| 需求处理 | Agent 自行补全平台、规模和体验边界        | 先确认平台、人数、内容优先级、监听方式和量产取舍                  |
| 运行架构 | 给出个人、群体和环境底声的通用分层           | 明确 NPC 筛选、发声体复用、相机与角色的监听分工，以及 Wwise 的播放限制 |
| 内容生产 | 主要描述运行时播放结构                 | 继续生成 POI、小组对话、精选表演和六语种模板                  |
| 验证方式 | 以 Voice、CPU 和 Profiler 建议为主 | 同时设计 Series S 性能、听感、传送、事件和长时间重复测试         |
| 后续修改 | 需要从整份答案中重新梳理受影响的部分          | 可以从决策地图查找相关决定、研究和验证计划                     |

Wayfinder 让这次讨论从架构草图推进到了制作规范和验证计划，各项选择也保留了依据。

## 从追问到执行的完整案例
前三个案例展示了追问如何改变方案。下面用一个脚步声 MVP（最小可行原型），演示如何串联 Matt Pocock 的多个 Skills，从查资料、做原型一直推进到规范文档、拆任务和实现功能。

这个案例受 Brennan Anderson 的《Has AI Replaced Technical Sound Designers?》（https://www.asoundeffect.com/has-ai-replaced-technical-sound-designers/）的启发，在文章中，他用了一个基础的脚步声触发需求来测试 AI 的技术音频设计能力：
- 面对大量动画，他希望省掉手工标记脚步的工作，让系统根据脚和地面的距离自动触发声音
- AI 很快做出了平地版本，也加入了离地后才能再次触发的逻辑，但遇到斜坡仍会提前发声，几轮补偿和参数调整都不理想
- Brennan Anderson 最后自己画图分析，把探针移动到脚后方约 6–12 英寸，才得到能够接受的效果

Brennan 的文章没有提及使用 Matt Pocock Skills。因此我想以类似的问题，演示这套工作流能否帮助我更早明确错误取舍，并把验证方法纳入开发过程，让 Agent 能够连续推进实现和自动检查。

### 需求：脚步声正确触发
> Foot IK：脚部反向运动学，会根据地面位置调整腿脚姿态，让脚尽量落在踏面上

我的要求是不挂动画通知（Notify），也不使用骨骼加速度来判断步点，希望根据脚与地面的接触，在楼梯和斜坡上准确触发脚步声。

我还补充了一个限制：项目的 Foot IK 不够理想，脚还没跨上台阶，就可能提前穿进台阶立面。如果把第一次碰撞直接当作落脚，脚步声就会提前播放，甚至连续误触发。

因此真正需要解决的问题是，什么样的碰撞，才有资格被判定为一次脚步触发。

### /grill-with-docs：定义问题
这里需要用 `grill-with-docs`，与 `grill-me` 不同的是，它会将讨论的结果落实到文档，供后续步骤使用。

启动技能后，它连续询问碰撞方式、错误取舍、可行走表面、穿透、跳跃、原地动作、离地距离、连续帧确认和初始化行为。

逐项回答完毕，触发规则明确了：
- 必须先确认脚已经离地，再确认有效落地，才能播放一次脚步声
- 状态机只需要记住脚处于落地状态（`Planted`），还是已经离地、可以等待下一次落脚（`Armed`）

```text
Planted
→ 连续确认 Air
→ Armed
→ 连续确认 Contact
→ 触发脚步并回到 Planted
```

每帧的检测结果被分成四类：
- `Contact`：命中可行走表面，脚底距离踏面满足 `0 ≤ 距离 ≤ 3 cm`
- `Air`：没有命中，或者脚底距离踏面满足 `距离 ≥ 7 cm`
- `Hold`：距离满足 `3 cm < 距离 < 7 cm`，保持当前状态
- `Invalid`：检测起点已经穿透、命中不可行走表面，或者脚底低于踏面

这一步确定的方案是：以左右脚底位置为输入，从其上方沿世界坐标的 `-Z` 方向发出短射线。命中后，用 `CharacterMovementComponent::IsWalkable(Hit)` 判断表面是否可行走，再计算脚底与命中点的竖直距离，结合穿透情况，得到上述四类检测结果。

每只脚独立记录状态：连续确认 `Air` 后进入 `Armed`，随后连续确认 `Contact`，才触发一次脚步声并回到 `Planted`。`Hold` 和 `Invalid` 都不发声，保持正式状态，同时打断尚未完成的连续确认。

注意：这里的距离阈值是原型的起始参数，后续需要结合项目中的角色、动画和检测方式调整。

### /research：检查前提
`grill-with-docs` 明确了这条路线的要求，但它是否适合作为常规生产方案，还需要验证。

因此我用 `research` 查阅官方文档和第三人称游戏的公开技术分享，在收集的资料中，更常见的做法是：

```text
Notify 或 Marker 决定步点
→ 从对应脚向下 Trace
→ 查询 Surface 和 Physical Material
→ 把速度、鞋型和材质传给 Wwise
```

Research 还整理了几条常见路线：

| 路线                              | 常见用途与限制                                                 |
| ------------------------------- | ------------------------------------------------------- |
| 手工 Animation Notify / Event     | 普通走跑最常见的做法，步点明确，但大量动画需要标记和维护                            |
| 骨骼高度或速度离线生成 Notify / Marker     | 适合批量处理 Mocap、重定向动画和 Motion Matching 数据，运行时仍走成熟的动画事件管线   |
| 运行时骨骼位置、速度或加速度                  | 可用于程序化动作和系统性 Foley，但会受到 IK、动画混合、LOD、采样率和抖动影响，需要额外状态机与过滤 |
| Motion Matching 的足相位与 Notify 去重 | 姿态频繁重选可能重复触发相邻脚步，因此仍需要标记、足相位或 Recency Filter            |
| 脚部 Collider 的 Hit / Overlap     | 更适合布偶、身体撞击、机械腿和真实物理驱动物体；普通走跑容易受穿模、碰撞抖动和动画裁剪影响           |

根据这次调查，可将前面的方案定位为一个条件明确的技术 MVP：验证不依赖 Notify 和骨骼加速度时，接触检测能做到什么，以及哪些情况下会误触发或漏触发。

`grill-with-docs` 确定了要验证什么，`research` 技能则提供了与其他生产方案比较的依据。

### /prototype：最小成本验证原型
只看状态机，很难判断算法的真实效果，适合先做一个原型。

这里使用 `prototype`，以 HTML 和 Three.js 制作了网页原型，方便调整参数、观察边界情况，也省去了准备 UE 工程和编译的时间。

这个原型用于观察局部的脚步触发规则。如果要验证真实角色动画、碰撞和 `CharacterMovement` 的配合，还是需要在 UE 中完成。

制作原型前，我又补了三种可以随时切换的 IK 压力模式，用来稳定复现不同的脚部状态，作为算法的测试输入：

| 测试模式      | 模拟的问题                  | 应该看到什么                                                              |
| --------- | ---------------------- | ------------------------------------------------------------------- |
| 正常抬脚      | 脚正常离开地面，再落到踏面          | 完成 `Air → Contact`，每次落脚触发一次                                         |
| 低抬脚 / 穿立面 | 抬脚高度不足，摆动途中穿过台阶立面      | 撞到台阶立面属于 `Invalid`，不发声；真正到达踏面后再按状态触发                                |
| 踏面穿透      | 脚底短暂低于水平踏面，随后被 IK 修正回来 | 脚底低于踏面时（`GroundGap < 0`）不发声；回到合法 `Contact` 后，是否触发取决于此前有没有进入 `Armed` |

下面的视频演示了原型，在平地、斜坡和楼梯移动，并切换了三种不同的 IK 模式来验证原型算法是否有效；触发脚步事件时，地面会出现一个小圆环。

### /to-spec：写成规范
网页原型让我确认了值得继续验证的状态规则。接下来，用 `to-spec` 把已经作出的决定整理成需求文档，明确后续要实现什么、怎样验收。

规范先明确了交付范围，这一阶段只交付可以操作和试听的技术 MVP，Foot IK 修复和量产脚步系统不在范围内。

规范也明确了两类验收：
- 自动化测试：一部分检查检测结果与状态转换，另一部分在测试场景中覆盖走路、跑步、正走和倒退，检查事件触发时机与次数
- 人工验收：在 PIE（Play In Editor，编辑器内运行）中走完整条路线，结合声音、屏幕调试信息（HUD）、射线和触发圆环检查结果

### /to-tickets：拆成任务
随后使用 `to-tickets`，将需求文档拆成任务单：

| 任务单          | 交付结果                      | 怎样检查                            |
| ------------ | ------------------------- | ------------------------------- |
| 搭建可重复测试路线    | 平地、八级上楼、平台、八级下楼和斜坡组成的连续路线 | 角色可以在 PIE 中正向、反向走完全程，台阶保留真实踏面碰撞 |
| 加入三种 IK 压力模式 | 正常抬脚、低抬脚穿立面和踏面穿透可以随时切换    | 模式只改变测试输入，不修改脚步状态机，也不会让角色失控     |
| 接入可听的双脚检测    | 左右脚状态机、调试声音、HUD、射线和触发圆环   | 自动化测试通过，并在平地走跑时完成一次人工试听         |
| 完成完整路线验收     | 三种模式、走跑和三档慢放的测试矩阵         | 检查楼梯、斜坡、倒退、切换和长时间运行，最后再做可听、可视验收 |

四张任务单按依赖推进：搭好测试场景，加入可重复的错误输入，接入检测，再跑完整测试矩阵。

### /implement：调度执行
最后使用 `implement`，按需求单顺序推进任务。因为任务的背景、开发决策、验证方法已经确定，这里 Agent 会执行一个 AFK（Away From Keyboard）的长程任务，自动完成开发。

Agent 会通过 UE 5.8 MCP 操作编辑器，并完成搭建测试场景、编写 C++ 逻辑、自动测试，并在完成后找用户试听和验证结果。

在这个 Agent 完工后我做了几轮小调整，主要是场景比例、模式切换等细节，但核心算法不变。

## 如何使用 Matt Pocock Skills
### 安装
> 注：文中所用的 Matt Pocock Skills 的版本为 v1.2.3

 要安装 Matt Pocock 的 Skills：
- 最简单的安装方法，将 `https://github.com/mattpocock/skills` 发给 Agent，让它来安装即可
- 若熟悉 `npx skills`，可使用 `npx skills@latest add mattpocock/skills` 来手动安装

安装时只需选择 `Mattpocock Skills`，不用选择 `Other`（这是 Matt 的预研 Skills）。

### 选择 Skill
Matt Skill 中有多个用途不同的 Grilling Skill：
1. 一次性的方案讨论或头脑风暴：用 `grill-me`
2. 讨论结果还要用于写文档、做原型或开发：用 `grill-with-docs`，把术语和决策保存下来
3. 工作量大、路线还不清楚，且多个决定相互影响：用 `wayfinder`，通过决策地图逐步推进

不想记住这些区别时，最简单的方法是直接使用 `ask-matt`，把当前问题交给它判断。

### 其他 Skill
除了文中提及的 Skill，下面几个也很适合音频工作：
- 当 AI 说了听不懂的“黑话”时，使用 `wait-what`，让它补充背景并换成更简单的说法
- 需要向程序、策划、编剧、录音棚或本地化团队确认信息时，使用 `to-questionnaire` 把待确认内容整理成问询单。不过发出去前最好自己检查一遍，别让 Agent 一口气列出几十个问题，把同事逼疯
- 想持续学习一个主题时，使用 `teach`。它会围绕学习目标整理资料、课程和练习，并保留后续学习所需的记录，方便接着上次的进度继续

### Grilling 的使用边界
查一个参数、解释一段代码这类目标明确的问题，直接问 AI 通常就够了。

当方案涉及多项取舍、改错成本较高，或者自己也没想清楚要什么时，再启用 Grilling。

## 对音频工作的思考
### 不只是编程工具
除了文中已经演示过的音效用例（拆解声音设计需求）和技术音频用例（技术选型及方案开发），这套 Skills 也适用于其他音频工作。

作曲面对“战斗音乐再激烈一点”，声音设计面对“武器更有力量”，录音需要确认角色语气和返录标准时，都可以先让 Agent 协助梳理判断条件。

### 让任务自动推进
有了完整的规范文档和任务单，就可以让 Agent 按顺序自动选择任务、执行、检查结果、推进下一步。这种持续推进任务的循环，也就是所谓的 Loop Engineering。

比如可以实现这样的效果：白天定好方向，晚上让 Agent 查资料、并行推进多种方案，第二天集中试听和检查结果。

但想实现这种“批量收菜”的开发模式，除了使用 Matt Pocock 这类工程框架明确需求和执行顺序以外，更重要的是提前配好外部工具（通过 Skill 或 MCP），这样在长任务的执行过程中，才能让 Agent 自行检查结果，减少反复摸索和人工确认。

### 人还要做什么
Agent 可以快速查资料、比较路线和实现方案。人仍需要明确需求、作出取舍，并结合声音的叙事作用、听感和审美，判断结果是否表达了预期的意图、是否适合放进游戏。

Grilling 也不是解决问题的万金油。它能帮助澄清模糊需求，但如果目标过于庞大，或缺少必要的背景信息，追问也可能偏离实际需求。

**但可以预见的是，技术实现的成本会继续降低，而决策和设计能力会愈发重要。能否讲清问题、做出取舍、判断结果，决定了 AI 使用者最终的产出质量。**

## 总结
本文通过几个案例，分享了 Matt Pocock Skills 的使用方式：
- 用 Grilling 补齐会影响方案的条件，尽早确认目标和取舍
- 用 `research` 查证前提，用 `prototype` 把关键规则做成易于观察的原型
- 用 `to-spec` 和 `to-tickets` 保存决定、拆分任务单，再交给 `implement` 推进实现

这套 Skills 最有价值的地方，就是在方案设计阶段问出那些过去要到返工时才补充的条件，让后续决策有更充分的依据。

随着基座模型的能力增强，我越来越看好 Matt Pocock 这类以简洁流程引导 Agent 的 Skills，先帮助人把问题想清楚，再让模型发挥能力。

希望这套工作流能帮大家把需求想得更清楚，让 AI 产出更好的结果。
